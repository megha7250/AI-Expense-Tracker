# API Integration Map

Generated by reading the actual Spring Boot source (`com.example.et_core`) —
every route below is real. Nothing here is invented; where the frontend has
UI for something the backend doesn't support, it's called out explicitly at
the bottom.

**Base URL:** `VITE_API_BASE_URL` (default `http://localhost:8080`)
**Auth:** `Authorization: Bearer <token>` header, added automatically by
`src/api/client.ts` for every request except `/api/auth/**`.

---

## Auth — `AuthController`

| Method | Path | Request | Response | Notes |
|---|---|---|---|---|
| POST | `/api/auth/register` | `{ name, email, password }` | `AuthResponse` (201) | Registers then immediately logs in server-side |
| POST | `/api/auth/login` | `{ email, password }` | `AuthResponse` (200) | |

```ts
AuthResponse = { accessToken, tokenType, expiresInSeconds, onboarded }
```

**No refresh-token endpoint exists.** `JwtUtils.generateRefreshToken` is defined
but never called from any controller. Access tokens are short-lived
(6000s / ~100 min in `application.yml`). The frontend does **not** fake a
refresh flow — a 401 anywhere logs the user out and redirects to `/login?expired=1`.

The JWT `sub` claim is the user's **UUID** (`AppUser.id`), not their email —
confirmed via `AppServiceImpl.loadUserByUsername`, which builds `UserDetails`
with `username = appUser.getId()`. `@AuthenticationPrincipal String userId`
across every controller expects this UUID.

## Onboarding — `OnboardingController`

| Method | Path | Request | Response |
|---|---|---|---|
| POST | `/api/onboarding` | `OnboardingRequestDto` | 200, empty body |

```ts
OnboardingRequestDto = {
  bankId, lastFourDigits, bankBalance,
  cardType?, cardLastFourDigits?, cardLimit?,
  cashBalance?, defaultPaymentModeId, languagePreference?
}
```
Creates a bank `Account`, an optional `Card`, a cash `Account`, and the user's
`UserConfig` in one transaction. Throws `UserAlreadyOnboardedException` (400)
if `UserConfig` already exists for the user.

## Accounts — `AccountController`  — **read-only**

| Method | Path | Response |
|---|---|---|
| GET | `/api/accounts` | `AccountDto[]` |

```ts
AccountDto = { id, bankName, lastFour, type: 'Savings'|'Cash'|'Credit', amount }
```
There is **no** POST/PATCH/DELETE for accounts. Accounts only come into
existence through `/api/onboarding`.

## Banks — `BankController` — **read-only**

| Method | Path | Response |
|---|---|---|
| GET | `/api/banks` | `Bank[]` (`{ id, name }`) |

Seeded once at startup by `DataSeeder` (11 major Indian banks).

## Payment Modes — `PaymentModeController` — **read-only**

| Method | Path | Response |
|---|---|---|
| GET | `/api/payment-modes` | `PaymentModeResponseDto[]` (`{ id, name, type: 'ASSET'|'LIABILITY' }`) |

Seeded once at startup (Credit Card, Debit Card, Net Banking, UPI, Cash, Digital Wallet).

## Categories — `CategoryController` — **read-only**

| Method | Path | Response |
|---|---|---|
| GET | `/api/categories` | `CategoryDto[]` (`{ id, name, isSystem }`) |

Combines 15 seeded `SystemCategory` rows with the caller's `UserCategory`
rows. **Sign convention:** system category ids are positive; user category
ids are returned negated (`-uc.getId()`). The same convention is required
when creating/updating a transaction's `categoryId`.

## Transactions — `TransactionsController`

| Method | Path | Request / Params | Response |
|---|---|---|---|
| GET | `/api/transactions` | `startDate?, endDate?, minAmount?, maxAmount?, types?[], categoryIds?[], accountIds?[], paymentModeIds?[], search?, page, size, sort` | `Page<TransactionDto>` (Spring Data page envelope) |
| GET | `/api/transactions/recent` | — | `TransactionDto[]` (last 5) |
| POST | `/api/transactions` | `TransactionRequestDto` | `TransactionDto` (201) |
| PATCH | `/api/transactions` | `TransactionRequestDto` (with `transactionId`) | `TransactionDto` (200) |
| DELETE | `/api/transactions/{id}` | — | 200, empty |

```ts
TransactionDto = { transactionId, type, description, amount, transactionDate, transferId, category }
TransactionRequestDto = {
  transactionId?, type, description, amount, transactionDate: "dd-MM-yyyy",
  paymentModeId, accountId, categoryId?, toAccountId?, transferId?
}
```

**Signed amounts:** the backend negates `amount` server-side for
`EXPENSE` and for the source leg of a `TRANSFER`. The frontend always sends a
**positive magnitude** and lets the backend apply the sign; when reading, a
negative `amount` means money left an account.

**Balance validation:** `InsufficientAccountBalanceException` → 400 if an
`ASSET`-type payment mode would take a balance negative.

**Ownership validation:** `AccountNotOwnedByUserException` (404) if an
account/toAccount id isn't owned by the caller.

## Analytics — `AnalyticsController`

| Method | Path | Params | Response |
|---|---|---|---|
| GET | `/api/analytics/cashflow/daily` | `startDate, endDate` | `DailyCashFlowProjection[]` |
| GET | `/api/analytics/cashflow/monthly` | `startDate, endDate` | `MonthlyCashFlowProjection[]` |
| GET | `/api/analytics/insights` | — | `AiInsightResponseDto[]` |
| GET | `/api/analytics/category-distribution` | `startDate, endDate` | `CategoryDistributionDto[]` |

`AiInsightResponseDto` insights are generated by a scheduled job
(`AiInsightScheduler`) server-side — the frontend only reads them, it never
triggers generation.

## AI Input — `AiController`

| Method | Path | Request | Response |
|---|---|---|---|
| POST | `/api/ai-input` | `{ rawText }` | `{ id, message }` (immediate ack) |
| GET | `/api/ai-input/active` | — | `{ jobId, status }[]` |

This is **not** a chat/completion endpoint — it's async, one-shot parsing.
Submitting text kicks off a background job (`AiParsingTask`) that uses Spring
AI + Ollama to extract type/amount/category/date, then on success
auto-creates a `Transaction` using the user's **default account and default
payment mode** from `UserConfig`. The frontend never sees the parsed
transaction directly — it finds out via the SSE stream below or by polling
`/api/transactions/recent`.

## Notifications (SSE) — `NotificationController`

| Method | Path | Params | Response |
|---|---|---|---|
| GET | `/api/notifications/subscribe` | `sessionId` | `text/event-stream` |

Events emitted: `CONNECTED`, `TRANSACTION_CREATED/UPDATED/DELETED`,
`CATEGORY_*`, `ACCOUNT_*`, `USER_*` (defined but not currently published by
any service), `AI_TASK_CREATED/PROCESSING/COMPLETED/FAILED/ERROR/QUEUED`.
In practice only `CONNECTED` and the `AI_TASK_*` events (from
`EventHandler.saveResultAsTxn`) are actually published today.

**Important implementation detail:** this endpoint requires the `Authorization`
header like every other endpoint, but the native browser `EventSource` API
cannot send custom headers. `src/services/sse.ts` implements the SSE
protocol manually over `fetch()` + `ReadableStream` so the Bearer token can
be attached.

## Error shapes

- **401** (from `CustomAuthEntryPoint`): JSON `{ status, message, timestamp }`
- **Everything else** (from `GlobalExceptionHandler`): a **raw string** body,
  not JSON — e.g. `"Account not found with id 4"`. `extractErrorMessage()` in
  `src/api/client.ts` handles both shapes.
- **500** (uncaught): the literal string `"Something went wrong!"`

## Backend-not-implemented (UI exists, endpoint does not)

These are called out explicitly in the UI via the `<NotImplemented />` badge
so nothing pretends to work that doesn't:

| Feature | Where in UI | Why |
|---|---|---|
| Create/edit/delete category | Categories page | Only `GET /api/categories` exists |
| Create/edit/delete payment mode | Payment Modes page | Only `GET /api/payment-modes` exists |
| Create/edit/delete bank | Banks page | Only `GET /api/banks` exists |
| Link/edit/remove an account | Accounts page | Only `GET /api/accounts` exists; accounts are created solely via onboarding |
| Update profile name/email server-side | Settings → Profile | No `/api/user/profile` or `/me` endpoint; stored in browser only |
| Change password | Settings → Security | No password-change endpoint |
| Two-factor auth | Settings → Security | Not implemented server-side |
| Delete account | Settings → Danger Zone | No delete-account endpoint |
| Token refresh | Session handling | No refresh endpoint; session simply expires and redirects to login |
| Forgot / reset password | Not built | No such controller — a fake "check your email" screen would be dishonest, so it was omitted rather than faked |
